# 블로그 작성 양식 (writing-style)

> 도메인 규칙(PROJECT overlay). 이 블로그의 "좋은 글" 정의이자, 반복 요청을 막는 체크리스트다.
> CLAUDE.md 에서 `@.claude/rules/writing-style.md` 로 import 되어 글 쓸 때 자동 적용된다.
> dod-checker(결정론 검출)·design-grill(설계 질문)이 이 파일을 근거로 삼는다.
> 발행 안전(익명화·기밀 취급)은 `publish-safety.md`, 프론트매터는 `content-frontmatter.md`.

## 적용 대상

- `src/content/blog/**/*.{md,mdx}` (블로그 본문), `src/pages/about.astro` 등 산문 페이지

## 1. 구조와 서사

- **동기·문제부터 연다.** 냅다 본론(결과·방법)으로 들어가지 않는다. "왜 이걸 하게 됐나 / 무슨 문제를 풀려 했나"를 먼저. (예: 약물 추출 결과부터 X → 문서 정합성 문제부터 O)
- **제목은 문제를 한 문장으로, 센스있게.** 서술형·기능나열형("X를 Y로 하기: Z 실험기") 지양. 확 들어오는 한 줄. (예: "문서끼리 말이 맞는지, 매번 LLM에 묻기는 싫었다")
- **소제목(h2)도 요점을 담는다.** "결론", "lite는??" 같은 맨 라벨·의문형 금지. 그 섹션의 결론을 제목에 넣는다. 띄어쓰기도 확인. (예: "결론 부터" → "결론: 무작정 지우는 도구가 아니다" / "lite는??" → "lite 모드: 코드 변경 없는 안전한 대안" / "내부코드만, 외부API…" → "결과 비교: 언제 코드가 줄어들까?")
- **처음부터 끝까지 정합성.** 자기모순 금지. 초반 전제(예: 기밀이라 외부 못 씀)와 후반 결론(예: 그냥 클라우드 써라)이 어긋나면 안 된다. 한 실을 끝까지 끌고 간다.
- **갑툭튀 금지.** 새 섹션·수치·도구는 리드인과 함께 등장. (예: "비용" 섹션은 "로컬이 아니라 유료 모델로 돌렸을 때"라고 먼저 짚고 시작)
- **모순 소지는 그 자리에서 해명.** 코드·설정에 앞 얘기와 어긋나 보이는 게 있으면(예: 로컬 지향인데 config에 `gpt-4o-mini`) 바로 옆에서 왜인지 설명한다. (위조 금지, 설명으로 해소)
- **OREO.** 요점 먼저, 근거·예시, 재확인. **결정과 교훈 중심**("무엇을 만들었나"보다 "왜 그렇게 했나 / 뭘 배웠나").

## 2. 문체 (담백함 = AI 티 제거) [중요]

초안 뒤 반드시 이 관점으로 훑는다. 본인 이름으로 나가는 글이라 사람이 쓴 티가 나야 한다.

- 격언·잠언조 금지 ("도구의 값어치는 경계에서 드러난다")
- 균형 대구/안티테제 금지 ("X가 못 주는 것들이다", "Y가 답에 가깝다")
- 리본 묶는 마무리 금지 ("~겠다는 감을 이번에 얻었다", "~라는 점에서 의미가 있다")
- 군더더기 서두 금지 ("결론부터 말하면", "결론은 분명하다", "~는 명확하다", "한 줄로:")
- 과장·번역투 동사 금지 ("DocETL을 만났다" → "찾았다"). 담백한 동사로.
- 볼드 남발 금지. 한 섹션에 핵심 1~2개만. (표 안의 용어명은 예외)
- 기업 보고서 말투 금지 ("투자 대비 효과가 뚜렷하다" → "싸게 먹힌다")

**번역투(한글을 영어로 직역한 이질감) 제거** [이번 회차 최다 지적]:
- 2인칭 "당신" 금지. 한국 개발 블로그는 독자를 "당신"으로 안 부른다. "직접 해보면", "~하면 된다"로.
- 번역 메타포 금지. "나란히 놓으면 포갠다", "그림이 그려진다", "결과를 가른다" 류 직역 비유. 사실을 그냥 진술한다 ("수치를 비교하면 이렇다", "여기서 결과가 갈린다").
- 삼단 대구(rule of three) 금지. "다른 A, 다른 B, 같은 C" 리듬 = 전형적 AI 티.
- 번역체 명사화 금지. "무차별 삭제기", "귀속한다", "리뷰 가능한 판단", "~형태로 남는다" → 동사로 풀어 쓴다.
- 번역투 서두 금지. "흥미로운 건,"("Interestingly,") 류.
- 셀프체크: 초안이 "한글을 영어로 번역한 것 같은 이질감"이 들면 그게 신호다. 소리 내 읽어 어색하면 고친다.

선호하는 결: 짧고 직설적인 문장, "~더라 / ~면 된다" 구어, 사실·수치 위주. 자랑·정리보다 관찰.
**보고서 → 블로그 변환 시**: 개조식 `1) (1) (2)` 번호 나열을 서사·표·불릿으로 풀어 다시 쓴다.

## 3. 형식

- **앰대시(—, U+2014) 금지.** 콜론(:)·쉼표(,)·마침표(.)로. 본문 발견 = dod `[E]` FAIL. (엔대시 – 는 범위 표기 등 본래 용도면 허용)
- **표·불릿 우선.** 비교·나열·문제 목록·단계는 산문 대신 표/불릿으로. 벽글 금지.
- **긴 코드/블록은 접는다.** 5줄 넘는 코드·설정은 접기로. `.md` 에서도 되는 패턴:

  ```
  <details>
  <summary>펼치기 라벨</summary>

  ​```yaml
  ...코드...
  ​```

  </details>
  ```
  (여는 태그 뒤 빈 줄, 코드펜스, 빈 줄, 닫는 태그 순서를 지켜야 렌더된다.)
  **`<summary>` 라벨 필수**: 빠뜨리면 브라우저 기본 라벨("세부 정보")로 떠서 접힌 내용이 무제목으로 묻힌다. (grill 축 3에서 지적됨)
- **이미지는 빠짐없이 + 캡션.** 원본 그림 전부 넣고 `*그림 N. …*` 캡션. 스크린샷 속 민감정보(경로·API키·사내명) 먼저 확인.
- **첨부로 설득력.** 실제 실행 파일(설정 YAML·입력·출력)을 `public/files/<주제>/` 에 넣고 링크. 단 안전한 것만 (`.env`·기밀 변환본 제외).
- **구조도는 손 SVG.** 2레인 등 교차 없는 깔끔한 배치. Mermaid는 이 블로그 톤에 안 맞아 지양. 수학 개념도도 손 SVG.
- **여러 줄 원시 HTML은 `.mdx` 로.** 표·SVG 같은 다줄 HTML은 `.md` 에서 누락될 수 있다. 리치한 글은 `.mdx`.

## 4. 사실 · 날짜 · 안전

- **검증된 사실만.** 정량 수치·버전·프레임워크 동작 주장은 공식 소스로 재확인한 것만. **원본(내 보고서 포함)이 틀렸으면 고친다.** (dod `[G]`, grill 축 1)
- **공식 수치는 원문에서.** 웹 검색 요약·요약 fetch는 수치를 왜곡한다. README·벤치마크 파일 원문으로 재확인. (이번에 초안의 저자 벤치 "60~94%"가 실제 "−54%"였다.)
- **정량 비교엔 재현 조건을 밝힌다.** 남의 수치와 나란히 놓을 땐 에이전트·모델·버전·측정법을 명시. "측정 방식 동일"이 모델까지 같다는 인상을 주지 않는다. 조건이 다르면 표에 그 행을 따로 둔다. (grill 축 1)
- **pubDate = 원본 작성일.** 기존 문서 기반이면 파일 타임스탬프를 확인해 그 날짜로.
- **발행 안전 = `publish-safety.md`.** 기밀 문서를 외부(소비자 LLM·API)에 넣은 정황 서술 금지, 사내명·고객사·실명 익명화, 민감 자료는 "외부 반출 금지 제약"으로 프레이밍(그게 진짜 동기인 경우가 많다).

## 권장 워크플로

1. (문서 기반이면) 원본 읽기 + 이미지·민감정보 확인
2. 사실 검증 (공식 소스 대조)
3. 초안 (위 1~3절 구조·문체·형식)
4. AI 티 훑기 (2절 기준 셀프 리뷰)
5. `/grill`(판단) → `/dod`(앰대시·프론트매터·빌드·민감어) → 커밋 → push
