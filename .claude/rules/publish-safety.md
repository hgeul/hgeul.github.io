# 발행 안전 규칙 (publish-safety)

> 이 저장소는 **공개**다. `main` 에 push 하면 `hgeul.github.io` 로 자동 배포된다.
> harness-base 와 위험이 반전된다: 저장소를 숨기는 게 아니라, **공개 글에 기밀이 새는 것**을 막는다.
> 낮에 하는 일(사내 프로젝트·고객사·사내 인프라)의 정보를 익명화하지 않은 채 올리는 것이 최대 리스크다.

## 적용 대상

- 발행되는 모든 것: `src/content/blog/**`, `src/pages/**`, `public/**`, `src/consts.ts`

## 규칙 (하면 안 되는 것)

- **실명 고유명사 금지.** 고객사명·사내 프로젝트 코드명·팀명·동료 실명을 그대로 쓰지 않는다.
  일반화한다: "한 금융 고객사", "사내 IAM 프로젝트", "결제 도메인" 처럼.
- **사내 식별자 금지.** 내부 호스트명·사설 IP(`10.`/`172.16-31.`/`192.168.`)·내부 URL·DB 이름·JIRA 티켓 키·리포지토리 경로.
- **시크릿 절대 금지.** 토큰·API 키·비밀번호·프라이빗 키·커넥션 스트링. 예시가 필요하면 명백한 더미(`sk-xxxx`, `example.com`).
- **재현 가능한 독점 코드 금지.** 회사 코드베이스를 알아볼 수 있는 통짜 스니펫 대신, 개념을 재작성하거나 최소 예제로.
  - **도메인만 가명이면 부족하다. 사내 프레임워크 지문도 지운다.** 커스텀 애노테이션(`@Route`), 쿼리빈(`QCommandEntity`), 헬퍼(`castReq`/`writeRes`), ORM fluent 시그니처(`.findOneOrNull()`) 같은 관례는 같은 팀 사람이 코드베이스를 특정하게 한다. 표준/의사코드로 중화해 "개념 최소 예제"로 제시하고, summary·문구로도 실제 코드가 아니라 예제임을 밝힌다.
- **기밀 자료를 다룬 정황을 사실대로 쓰지 않는다.** "사내 문서를 ChatGPT에 붙여넣었다"처럼 기밀 문서를 외부 서비스(소비자 LLM 등)에 넣은 정황을 공개 글에 적으면 정보보안·NDA 위반을 자백하는 셈이다. 실제로 했든 안 했든 그런 인상을 주는 서술 금지. **접근 방식·기법은 일반론으로, 실험은 공개/샘플 데이터로** 서술하고, 민감 자료는 "외부에 못 넣는 제약"으로 프레이밍한다(그게 오히려 진짜 동기인 경우가 많다).

## 검출 방식 (denylist 는 저장소 밖)

민감 고유명사(회사명 등)를 이 파일에 하드코딩하면 그 자체가 공개 repo 로의 유출이다.
→ denylist 는 `.gitignore` 처리된 로컬 파일에 둔다:

```
.claude/sensitive-terms.local     # 한 줄에 하나. git 에 안 올라감. 각자 채운다.
```

- dod-checker `[M]` 과 pre-commit 훅이 이 파일이 있으면 로드해, 발행 대상 텍스트에서 해당 단어를 스캔한다.
- 없으면 정규식 기반 스캔(사설 IP·`Authorization: Bearer`·키 패턴)만 수행하고, denylist 미설정을 INFO 로 알린다.

## 근거

- 공개 저장소 + 자동 배포 = 한 번 push 하면 검색엔진·아카이브에 즉시 박제된다. 지워도 캐시가 남는다.
- 기술 블로그의 가치는 실전 경험인데, 그 실전은 대개 기밀 위에서 일어난다. 익명화가 발행의 전제 조건이다.

## 회색지대 / 예외

- 이미 공개된 오픈소스·공식 문서의 고유명사는 그대로 써도 된다 (Astro, Kubernetes 등).
- 본인 공개 계정(GitHub `hgeul`)·이 블로그 자체 정보는 공개 대상이다.

## 관련

- 검증: dod-checker `[M]`(민감어·시크릿), design-grill 축 2(익명화), pre-commit 훅
