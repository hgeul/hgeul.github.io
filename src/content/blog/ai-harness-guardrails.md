AI에게 초안을 맡기기 시작하면서 몇 번 데었다.

한번은 초안이 인용한 벤치마크 숫자가 그럴듯해서 그대로 쓸 뻔했는데, 원문을 열어보니 부호가 반대였다. 다른 날엔 사내 실험 회고를 익명화해 올리다가, 곁에 딸린 결정 기록에 익명화 전 원문 이름이 남아 공개 저장소로 새어 나갈 뻔했다. 그리고 며칠만 지나면 "이걸 왜 이렇게 정했더라"가 매번 사라졌다.

세 번 다 원인이 같았다. AI가 생산을 대신하니 빨라졌지만, 빨라진 만큼 검증할 게 쌓였고, 그걸 매번 사람 기억과 규율에 기대고 있었다는 것이다.

그래서 매 턴 자동으로 로드되는 하네스를 짰다. 생산은 AI에 맡기되, 빠른 속도가 정확성과 기밀을 갉아먹지 않도록 사람 규율이 아니라 **기계로** 붙잡아 두는 장치다. 이 글은 그 원리다. 구현 파일을 통째로 붙이는 대신, 어떤 문제를 어떤 방식으로 막았는지를 남긴다.

## 요지: 사람의 일을 생산에서 검증으로 옮긴다

**사람이 하는 일을 "생산"에서 "검증"으로 옮기고, 그 검증을 사람 규율에 기대지 않고 기계에 박아둔다.** 규율은 피곤할 때 제일 먼저 무너지니까, 기본값 자체가 안전한 편이 낫다.

이걸 여섯 가지 방식으로 나눴다.

| 방식 | 막는 것 |
|---|---|
| 재사용 골격 / 도메인 오버레이 분리 | 재사용성 + 기밀 경계 |
| 경계를 넘는 것만 철저히 검증 | 검증 피로(인지부채) |
| 판단과 결정론을 다른 도구로 | 검증 누락 |
| 기밀은 규율이 아니라 gitignore로 | 공개 유출 |
| "왜"를 결정 기록으로 박제 | 의도 증발(의도부채) |
| 코드를 진실로, 문서는 드리프트 검사 | 문서 썩음 |

## 1. 골격과 도메인을 분리한다

하네스를 두 층으로 나눴다.

- **BASE**: "어떻게 만드는가"의 절차·엔진. 프로젝트와 무관하다. 워크플로, 검증 도구, 훅 로직이 여기 있다.
- **오버레이**: "무엇이 옳은가"의 도메인 판단. 프로젝트마다 새로 쓴다. 도메인 규칙, 진실 원천 지도, 결정 기록이 여기 있다.

이렇게 가르면 두 가지가 동시에 풀린다. BASE는 새 프로젝트에 그대로 복사해 재사용하고, 오버레이(특히 회사 일의 도메인 규칙·내부 문서)는 절대 밖으로 안 나간다. 지금 읽는 이 블로그도 같은 BASE 위에 "블로그용 오버레이"만 얹은 것이다. 오버레이는 매칭되는 파일을 **고치기 전에** 적용되도록 걸어둬서, 기술부채나 유출을 리뷰가 아니라 생성 단계에서 차단한다.

## 2. 다 검증하지 않는다, 경계를 넘는 것만

모든 결과물을 똑같이 검증하려 들면 지쳐서 아무것도 못 본다. 그래서 딱 하나만 철저히 본다. **경계를 넘는 것.**

이 블로그에서 경계를 넘는 것은 "공개 발행되는 텍스트"다. 그래서 발행 본문의 사실 정확성, 익명화, 빌드를 깨는 프론트매터는 철저히 보고, 내부 컴포넌트 스타일 미세조정은 가볍게 넘긴다. 회사 백엔드였다면 경계는 "외부로 나가는 응답·권한·마이그레이션"이 된다. 블로그냐 백엔드냐만 다르지, 경계부터 본다는 건 같다. 가능한 검증은 자동화(빌드, 정적 검출)로 넘기고, 사람의 주의는 경계 넘는 결과물에만 쓴다.

## 3. 판단과 결정론을 섞지 않는다

발행 직전 검수를 두 도구로 나눴다. 실패 방식이 다르면 잡는 도구도 달라야 하기 때문이다.

| | 결정론 검수 | 판단 검수 |
|---|---|---|
| 무엇 | 기계로 딱 떨어지는 규칙 | 기계가 못 잡는 판단 |
| 예 | 앰대시, 프론트매터 누락, 시크릿 패턴, 커밋 형식, 빌드 | 수치가 진짜 측정값인가, 익명화가 충분한가, 구조가 말이 되나 |
| 결과 | PASS / FAIL / WARN | 소크라테스식 질문 목록 |
| 자동수정 | 안 함(보고만) | 안 함, 점수도 안 매김 |

이렇게 나누는 이유는 grep으로 끝날 일을 사람에게 시키지 않으려는 것이다. 반대로 "이 수치 진짜 측정한 거냐" 같은 판단은 기계에 넘겨짚게 하지 않는다. 판단 검수의 답은 그대로 버리지 않고 결정 기록으로 넘어간다(아래 5번).

## 4. 기밀은 규율이 아니라 gitignore로 막는다

이 저장소는 공개다. push 하면 검색엔진에 즉시 박제되고, 지워도 캐시가 남는다. 그러니 "조심하자"는 관례로는 부족하다. 기본값 자체가 안전해야 한다.

두 가지를 기계에 박았다.

- **민감어 목록은 저장소 밖에.** 회사명·동료 실명 같은 걸 규칙 파일에 하드코딩하면 그 자체가 유출이다. 그래서 목록은 gitignore된 로컬 파일에 두고, 커밋 훅과 검수기가 그 파일이 있으면 로드해 발행 대상 텍스트를 스캔한다.
- **내부 문서는 커밋 경계 밖에.** 결정 기록·정책 같은 `docs/` 폴더를 gitignore가 기본으로 뺀다. 공개 저장소여도 내부 작업노트가 커밋 경계에 들어오지 않는다.

두 번째 규칙은 한 번 데고 나서 굳혔다. 이 블로그에 사내 실험 회고를 익명화해 올릴 때, 발행 본문은 깨끗했는데 함께 커밋하려던 **결정 기록에 익명화 전 원문 고유명사가 남아** 있었다. 결정론 검수기가 그걸 FAIL로 잡아 발행을 멈췄다. 사람이었으면 "본문 깨끗하니 됐지" 하고 넘겼을 자리다. 그 뒤로 결정 기록 폴더 자체를 커밋 경계 밖으로 빼서, 다음부터는 스캔에 걸리기 전에 아예 안 올라가게 했다.

## 5. "왜"를 박제한다

코드는 "무엇을 했는가"만 남긴다. "왜 그렇게 했는가"는 다음 날이면 사라지고, 반년 뒤엔 과거의 내가 왜 그랬는지 나조차 모른다. 이걸 의도부채라 부르기로 했다.

그래서 판단이 필요한 작업마다 결정 기록(ADR)을 남긴다. 무엇을 정했는지만이 아니라, **어떤 수치를 어디서 확인했는지, 무엇을 어떻게 익명화했는지, 이 판단이 언제 깨지는지(만료 조건)**를 같이 적는다. 앞의 RAG 회고 글도 발행 전 "이 숫자 진짜 측정한 거냐"는 질문을 여럿 받았고, 그 문답과 확인한 근거를 전부 결정 기록에 박아뒀다. 다음에 같은 주제를 만질 때 그 기록부터 다시 읽으면, 반년 전의 나를 처음부터 심문할 필요가 없다.

## 6. 코드를 진실로 두고, 문서는 드리프트를 검사한다

문서와 규칙은 코드보다 빨리 낡는다. "이 설정은 파일 X의 Y줄"이라 써둔 규칙이, 정작 코드가 바뀌면 거짓말이 된다.

그래서 "진실 원천 지도"를 따로 둔다. 무엇의 진실이 어디(어느 코드·설정)에 사는지를 등록해두고, 드리프트 검사기가 이걸 기준으로 어긋남을 세 단계로 본다.

- **1단계(결정론)**: 사라진 파일·범위 밖 줄을 가리키는 앵커. 기계로 딱 잡힌다.
- **2단계(판단)**: 코드·설정과 모순되는 주장. 여기는 LLM이 읽고 판단한다.
- **3단계(신선도)**: 만료 조건·오래된 기록.

문서가 코드와 어긋나면 고치는 건 문서 쪽이다. **코드가 진실**이고, 규칙 문서가 코드를 이기는 일은 없다.

## 그래서 어떻게 시작하나

한 번에 이걸 다 만들 필요는 없다. 내 경우 순서는 이랬다.

1. 매 턴 자동 로드되는 지침 파일 하나(`CLAUDE.md`)에 워크플로와 검증 우선순위부터 적는다.
2. 발행/커밋 직전 결정론 검수 하나를 붙인다(앰대시·시크릿·빌드 같은, grep으로 끝나는 것부터).
3. 기밀이 나갈 수 있는 프로젝트면 gitignore와 민감어 목록을 **먼저** 박는다. 이건 나중에 붙이면 이미 샌 뒤다.
4. 판단이 필요한 순간에 결정 기록을 남기는 습관을 들인다.

이 셋업은 개인 생산성용이고, 지금도 계속 바뀐다. 한두 달 뒤엔 꽤 달라져 있을 거다. AI에 생산을 넘긴 만큼 어디를 검증할지 좁게 정하고, 그걸 기계로 지킨다. 이 하네스가 하는 일은 그게 전부다.
