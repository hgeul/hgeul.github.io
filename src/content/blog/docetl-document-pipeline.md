발단은 문서 더미였다. 제안요청서(RFP), 제안서, 기획서, 스펙정의서처럼 크고 서로 얽힌 문서들을 다뤄야 했는데, 조건이 까다로웠다.

- **정합성 확인**: 한 문서의 요구가 다른 문서의 스펙과 어긋나지 않는지 맞춰봐야 한다.
- **긴 문서**: 하나하나가 길다.
- **교차 대조**: 여러 문서를 서로 겹쳐 봐야 한다.
- **외부 반출 금지**: 이런 문서는 함부로 외부에 못 내보낸다.

그래서 대화형 LLM에 붙여넣는 것부터가 선택지가 아니었다. 데이터 통제를 빼고 봐도 대화형은 한계가 뚜렷하다. 같은 입력에도 답이 매번 달라지고(비결정성), 문서가 수십 개로 늘면 일관된 품질로 처리할 방법이 없고, 출력이 맞는지 자동으로 검증할 길도 없다. 문서 처리를 **대화가 아니라 엔지니어링 파이프라인**으로, 되도록 데이터가 내 손을 벗어나지 않게 다뤄야 했다. 그래서 찾은 게 DocETL이다.

이 글은 DocETL이 뭔지, 그리고 실제 기밀 문서 대신 공개 예시 데이터로 도구를 돌려본 결과를 정리한 것이다. 반복적이고 대규모인 문서 작업에는 확실히 맞는 도구고, 대신 "깔고 돌려놓으면 알아서 되겠지"는 아니다.

## DocETL이 뭔가

LLM 기반 문서 처리 파이프라인을 선언적 YAML로 정의하고 실행하는 프레임워크다. 복잡한 비구조화 데이터를 반복 가능하고 검증 가능한 구조화된 정보로 바꾸는 것을 강제한다.

끌린 지점은 세 가지였다.

- **선언적 인터페이스**: "무엇을" 할지를 YAML로 쓰면, "어떻게"는 프레임워크가 처리한다.
- **프롬프트 완전 제어**: Jinja 템플릿으로 동적 프롬프트를 만든다.
- **다양한 모델**: OpenAI, Anthropic, 그리고 Ollama를 통한 로컬 모델까지.

### 왜 대화형으로는 안 되나

기존 방식(ChatGPT/Gemini에 붙여넣기)은 이런 데서 막힌다.

| 문제 | 내용 |
|---|---|
| 재현성 부족 | 같은 입력에도 다른 결과 (비결정성) |
| 확장성 한계 | 수천 건을 일관된 품질로 돌릴 중앙 관리가 없음 |
| 검증 불가 | 출력 품질을 자동 검증·재시도할 메커니즘 부재, 수동 검사 의존 |
| 컨텍스트 제한 | 긴 문서를 한 프롬프트에 넣으면 토큰 한계 초과 |
| 최적화 어려움 | 어떤 프롬프트·구성이 최적인지 체계적으로 실험할 기반 없음 |

DocETL은 이걸 ETL(Extract, Transform, Load) 워크플로우로 다시 짠다. 선언적 정의 + Validation으로 안정성을 확보하고, Optimizer로 성능을 개선한다.

## 핵심 개념: 연산자, Optimizer, Validation

### 연산자(Operations)

파이프라인은 몇 가지 연산자를 조합해 만든다.

| 연산자 | 하는 일 | 예 |
|---|---|---|
| **Map** | 각 문서에 개별적으로 LLM 적용, 추출·변환 | 약물명 추출, 감정 분석 |
| **Reduce** | 여러 문서를 그룹화해 집계·요약 | 약물별 부작용 요약 |
| **Resolve** | 유사 엔티티를 식별해 통합(중복 제거) | "Tylenol"과 "acetaminophen" 통합 |
| **Unnest** | 리스트/배열 출력을 개별 레코드로 분할 | JSON 배열 → 관계형 행 |
| **Filter** | 조건에 따라 문서·레코드 제외 | |
| **Split + Gather** | 긴 문서를 청크로 나누고(Split), 각 청크에 주변 맥락을 덧붙여(Gather) 컨텍스트 유지 | 토큰 한계 우회 |

### Optimizer

사용자가 만든 파이프라인을 받아 여러 변형(Variants)을 만들고, 샘플 데이터로 각 변형을 돌려 처리 시간·비용·품질을 비교해 최적안을 고른다.

여기서 내가 처음에 오해한 지점이 있다. Optimizer가 "내가 짠 구조는 그대로 두고 blocking threshold·chunk size 같은 매개변수만 조정한다"고 생각했는데, 공식 문서를 다시 보니 그보다 더 나간다. DocETL의 optimizer(MOAR)는 **연산자 자체를 재작성·분해**한다. 예를 들어 긴 문서에 대한 Map을 `Split → 청크별 Map → Reduce`로 쪼개거나, 중간에 gleaning·resolve 스텝을 끼워넣거나, 모델을 바꾼 변형까지 만들어 비교한다. 파이프라인의 뼈대까지 손대는 구조적 최적화다.

### Validation

출력 데이터에 대한 Python 검증 조건을 YAML에 그대로 쓸 수 있다. 실패하면 자동 재시도한다.

```yaml
# 추출된 약물이 최소 1개 이상인지 확인해 추출 실패를 방지
validate:
  - len(output["medication"]) > 0
```

이 한 줄이 "출력이 비어 있으면 다시 시도"를 파이프라인 레벨에서 보장한다. 대화형에는 없던 안전장치다.

## 언제 쓰고, 언제 쓰지 말아야 하나

이건 아무 데나 쓰는 도구가 아니다.

| 잘 맞는 경우 (고빈도·대규모·일관성) | 안 맞는 경우 (단발성·탐색적·실시간) |
|---|---|
| 매일 들어오는 고객 피드백 수천 건 분류 | 단발성 요청 ("이 계약서 요약해줘") |
| 법률 문서에서 당사자·날짜·조항 반복 추출 | 탐색적 분석 (뭐가 있는지 모르고 시도) |
| 의료 기록 대량 처리·표준화 | 빠른 프로토타이핑 (ChatGPT가 더 빠름) |
| 논문 메타데이터 추출·구조화 | 실시간 대화형 (API 지연 때문에 부적합) |

한 번 쓰고 말 작업이면 대화형이 낫고, 수백 번 반복할 작업이면 DocETL 쪽이다.

## 직접 돌려본 실험

실제 사내 문서에 바로 붙이기 전에, 도구 감을 잡으려고 공개 예시류 데이터로 먼저 파이프라인을 짜봤다. 소재는 약물명으로 골랐다. DocETL 공식 자료가 테스트 예제로 약물 데이터를 권하는데, 이유가 도구의 핵심을 정확히 보여주기 때문이다. 약은 같은 성분인데 이름이 다르거나(브랜드명 vs 성분명), 같은 효능을 두고도 표기가 제각각인 경우가 많다. 이렇게 흩어진 이름을 식별해 하나로 통합(Resolve)하는 게 DocETL이 내세우는 강점이라, 감 잡기에 딱 맞는 소재였다.

목표는 이렇게 잡았다: 의료 진료 기록에서 약물명, 부작용, 용도를 추출하고 중복을 제거하기.

수동으로 4단계 파이프라인을 설계하고 각 연산자의 프롬프트를 직접 작성했다.

1. `extract_medications`: 각 transcript에서 약물명 추출
2. `unnest_medications`: 리스트를 개별 레코드로 분할
3. `resolve_medications`: 중복 제거 (Blocking threshold 0.5, 유사도 50% 이상만 비교)
4. `summarize_medications`: 약물별 부작용·용도 요약

실제 파이프라인 정의(YAML)는 이렇다. 위 4단계가 그대로 담겨 있고, 각 연산자의 프롬프트까지 직접 썼다. 길어서 접어뒀다.

<details>
<summary>파이프라인 YAML 전체 펼치기 (약 80줄)</summary>

```yaml
datasets:
  transcripts:
    path: medical_transcripts.json
    type: file

default_model: gpt-4o-mini

system_prompt:
  dataset_description: 의료 진료 기록 모음
  persona: 약물을 분석하는 의료 전문가

operations:
  - name: extract_medications
    type: map
    sample: 10
    output:
      schema:
        medication: list[str]
    prompt: |
      이 진료 기록에서 언급된 모든 약물을 추출하세요:
      {{ input.src }}
      약물 이름만 반환하세요. 없으면 빈 리스트를 반환하세요.

  - name: unnest_medications
    type: unnest
    unnest_key: medication

  - name: resolve_medications
    type: resolve
    blocking_keys:
      - medication
    blocking_threshold: 0.5
    comparison_prompt: |
      이 두 약물이 동일한 약물인가요? (브랜드명과 일반명도 같은 약물로 간주)
      약물 1: {{ input1.medication }}
      약물 2: {{ input2.medication }}
      예시: 타이레놀 = 아세트아미노펜, 프릴로섹 = 오메프라졸, 립토르 = 아토르바스타틴
    embedding_model: text-embedding-3-small
    output:
      schema:
        medication: str
    resolution_prompt: |
      이 약물명 변형들을 표준 명칭으로 통일하세요:
      {% for entry in inputs %}
      - {{ entry.medication }}
      {% endfor %}
      가장 일반적인 표준 약물명을 반환하세요.

  - name: summarize_medications
    type: reduce
    reduce_key:
      - medication
    output:
      schema:
        side_effects: str
        uses: str
    prompt: |
      {{ reduce_key }}에 대한 진료 기록들:
      {% for value in inputs %}
      {{ value.src }}
      {% endfor %}

      다음 정보를 한글로 제공하세요:
      1. 부작용: 어떤 부작용이 언급되었나요?
      2. 용도: 이 약물이 어떤 질환에 사용되나요?

pipeline:
  steps:
    - name: medical_analysis
      input: transcripts
      operations:
        - extract_medications
        - unnest_medications
        - resolve_medications
        - summarize_medications
  output:
    type: file
    path: medication_results.json
    intermediate_dir: intermediate_results
```

</details>

여기서 `default_model: gpt-4o-mini`가 눈에 걸릴 수 있다. "외부에 못 보낸다며?" 싶은데, 이건 이 실험이 **공개 샘플 데이터**라서 클라우드 모델을 그냥 쓴 것이다. 실제 기밀 문서에 적용한다면 이 한 줄을 로컬 모델(예: `ollama/llama3.1`)로 바꿔야 한다. 그리고 바로 그 로컬 전환이 아래에서 막힌 지점이다.

### 실행 결과

- 입력: 약물 정보 transcript 10개
- 중간: 약물명 15개 추출
- 최종: 11개로 통합 (예: Tylenol + acetaminophen → acetaminophen)
- Resolve 단계에서 가능한 비교 105개 중 91개만 실행. **blocking으로 API 호출 13% 절감.**

![DocETL 실험의 LLM API 사용량 대시보드](/images/docetl/api-usage.png)

*그림 1. 이 실험의 API 사용량. 총 46,875 토큰, 200 requests, 10월 예산은 $0.01 소진.*

### 예상 못 한 발견: 한글 응답이 2.4배 느리다

같은 파이프라인인데 응답 언어에 따라 처리 시간이 크게 갈렸다.

| 응답 언어 | 처리 시간 |
|---|---|
| 영어 | 1분 33초 |
| 한글 | 3분 48초 (약 2.4배) |

한글 프롬프트·응답을 처리할 때 토큰당 지연(latency)이 올라가는 현상이다. 한글이 토큰 효율이 낮다는 건 알려진 얘기지만, 파이프라인 전체 처리 시간에 2배 넘게 벌어지는 걸 직접 보니 체감이 달랐다. 다국어 대량 처리라면 이 비용을 설계 단계에서 계산에 넣어야 한다.

### 품질: 통합에 성공한 것과 실패한 것

중복 제거(Resolve)는 브랜드명과 일반명(성분명)을 정확히 맞춰 하나로 합치는 데 성공했다.

| 통합 전 | 통합 후 | 유형 |
|---|---|---|
| 타이레놀 + 아세트아미노펜 | 아세트아미노펜 | 브랜드명 → 성분명 |
| 리피토르 + 아토르바스타틴 | 아토르바스타틴 | 브랜드명 → 성분명 |
| 모트린 + 이부프로펜 | 이부프로펜 | 브랜드명 → 성분명 |
| 베나드릴 + 디펜히드라민 | 디펜히드라민 | 브랜드명 → 성분명 |

반면 일부는 여전히 별개 항목으로 갈라졌다. Resolve가 통합을 확신하지 못한 경우다.

| 분리된 항목 | 문제 |
|---|---|
| 오메프라졸 (성분명) | 프리로섹 OTC(같은 성분 다른 브랜드)와 통합 실패 |
| 프리로섹 OTC (브랜드명) | 오메프라졸과 통합 실패 |

같은 성분인데 브랜드가 다르면 놓치는 케이스가 남았다. Blocking threshold와 프롬프트를 추가로 미세 조정해야 한다는 뜻이다. 또 한글 출력이 일부는 한글, 일부는 영어로 섞여 나와 프롬프트 개선이 필요했다.

### 정작 필요한 로컬 모델은, 노트북이 못 버텼다

여기서 원래 목적이 다시 걸린다. 기밀 문서는 외부 API로 못 보내니, 진짜 쓰려면 모델이 내 손 안에서 돌아야 한다. **로컬 모델이 선택이 아니라 조건**이라는 뜻이다. 그래서 Ollama의 Llama 3.1 8B로 돌려봤다. 결과는 좋지 않았다.

![로컬 모델 실행 중 반복된 LLM 호출 타임아웃](/images/docetl/local-timeout.png)

*그림 2. 노트북 스펙 한계로 "LLM call timed out after 3 attempts"가 반복됐다.*

![작업관리자 성능 탭. CPU만 쓰고 GPU는 놀고 있다](/images/docetl/cpu-usage.png)

*그림 3. GPU는 거의 놀고 CPU만 40%대로 지속 사용. 이 환경에서 8B 모델은 버거웠다.*

타임아웃이 반복됐고, GPU는 쓰지 못한 채 CPU만 계속 물고 있었다. 구조화된 출력 품질도 클라우드 모델 대비 확연히 낮았다.

여기서 이번 실험의 진짜 딜레마가 드러난다. 학습이나 공개 데이터라면 클라우드(gpt-4o-mini)가 빠르고 싸서 그냥 쓰면 된다. 하지만 내 원래 목적인 기밀 문서엔 클라우드를 못 쓴다. 그러면 남는 질문은 하나다. 로컬 모델을 쓸 만하게 굴릴 하드웨어가 있느냐. 노트북 한 대로는 8B도 버거웠다.

## 문서 정합성 점검에 써볼 기준

이번 실험에서 확인한 범위는 이렇다.

- DocETL은 "문서 처리를 코드처럼 다루는" 도구다. 재현성·검증·재시도를 파이프라인 레벨에서 얻는다. 대화형으로는 안 되던 것들이다.
- 대신 초기 설계 비용이 있다. 연산자 조합과 프롬프트를 직접 짜야 하고, 엣지 케이스(같은 성분 다른 브랜드, 언어 혼용)는 여전히 사람이 튜닝해야 한다.
- 로컬이냐 클라우드냐는 데이터가 정한다. 클라우드에 보내도 되는 데이터면 gpt-4o-mini가 빠르고 싸다. 기밀 문서라면 로컬이 조건인데, 노트북 한 대로 쓸 만한 품질을 뽑기엔 아직 벅찼다.
- 반복·대규모·일관성이 필요한 작업이면 도입할 값어치가 있고, 단발성·탐색적 작업이면 그냥 대화형이 낫다.

처음 목표는 문서 정합성 점검이었다. 약물 이름을 통합한 Resolve의 방식이 문서마다 다른 용어와 요구사항을 맞추는 데도 이어질 수 있겠다고 봤다. 다만 기밀 문서에 적용하려면 먼저 처리 환경을 정해야 한다. 이 실험에서는 노트북의 로컬 모델이 그 조건을 만족하지 못했다.
