사내 RAG 프로젝트를 동료와 함께 몇 주간 굴리며 스택을 일곱 번 갈아엎었다. 무료 오픈소스 조합에서 시작해 자체 구성 스택으로 넘어갔고 마지막에는 형태소 분석 기반 지식 그래프까지 붙여봤다. 케이스마다 변수를 하나씩만 바꿔가며 측정했다. 이 글은 그 시행착오의 회고다. 어떤 구성을 만들었는지보다 예상과 달랐던 결과에 초점을 맞췄다.

## 실험에서 먼저 확인한 세 가지

1. **유료 임베딩이 더 빠르고 정확했다.** 무료 임베딩은 느리고 부정확했다. 유료 임베딩으로 바꾸니 정확도가 올랐지만, 처리 로직이 엉성하면 API 비용이 2,200배로 튄다. 배치 처리로 해결했다.
2. **이 규모에서는 Vector DB 교체 효과가 없었다.** Qdrant ↔ Milvus를 바꿔도 속도·정확도 차이가 없었다.
3. **Entity 기반 지식 그래프의 답변 기여도는 낮았다.** 카테고리 관계와 형태소 삼중항 모두 응집도가 낮았다. 답변 품질을 끌어올린 건 임베딩 유사도(`SIMILAR_TO`)였고, 이 실험에서는 Vector 검색과 유사도만으로 충분했다.

## 실험 설계

RAG는 문서를 임베딩해 Vector DB에 넣고, 질문과 유사한 조각을 찾아 LLM에 붙여 답을 생성한다. 여기에 "지식 그래프"를 얹으면 개념 간 관계까지 검색에 쓸 수 있다는 게 GraphRAG의 가설이다. 이 가설이 우리 데이터에서 실제로 값을 하는지가 핵심 질문이었다.

케이스마다 변수를 하나만 바꾸고 나머지는 고정했다. 측정 항목은 네 가지다.

| 항목 | 무엇을 보나 |
|---|---|
| 임베딩 속도 | 테스트셋 전체를 임베딩하는 데 걸린 시간 |
| 정확도 | QnA 테스트셋 기준 답변/검색 정확도 |
| API 비용 | 임베딩·생성에 든 실제 청구 비용 |
| Graph 응집도 | 지식 그래프 관계가 얼마나 의미 있게 연결됐나 |

초기 프레임워크로는 [ApeRAG](https://github.com/apecloud/ApeRAG)를 골랐다. 임베딩·생성 모델 조합, System Prompt, 그래프 관계 생성 로직을 직접 커스터마이즈할 수 있어서, 변수를 하나씩만 바꿔가며 비교하기에 맞았다. 이후 케이스에서는 Milvus/Qdrant + Neo4j로 자체 스택을 구성해 더 세밀하게 통제했다.

실험은 문서 1건에서 추출한 QnA로 돌렸다. 초기엔 160개, 후반 그래프 실험에선 약 900개 규모였다. 정확도 수치는 같은 질문을 각 10회씩 반복해 얻은 **대략치**다. 케이스 간 정밀 벤치마크가 아니라 방향성을 보는 값으로 읽으면 된다.

## 케이스 전체 흐름

| 케이스 | 바꾼 변수 | 임베딩 속도 | 정확도 | 핵심 결과 |
|---|---|---|---|---|
| 1 | 무료 임베딩+무료 생성 | 1시간+ | 40% 이하 | 실용성 낮음 |
| 2 | 유료 임베딩으로 교체 | 1분 이하 (60배↑) | 70%+ | Graph 응집도 매우 낮음 |
| 3 | 자체 스택 전환 | 1시간 10분+ | 미측정 | 비용 $22 폭탄 |
| 4 | 배치 임베딩+Vector DB 경량화 | 30초 이내 (140배↑) | 85%+ | 비용 정상화 |
| 5-1 | Neo4j 카테고리 관계 | 1분 이내 | 90%+ | Graph 응집도 여전히 낮음 |
| 5-2 | Vector DB 교체 (Qdrant→Milvus) | 1분 이내 | 90%+ | 차이 없음 |
| 6 | mem0 대화 메모리 | 측정 안 함 | 측정 안 함 | 맥락 유지, 토큰 감소 |
| 7 | KoNLPy 형태소 삼중항 | 측정 안 함 | 측정 안 함 | Entity < 유사도, Graph 기여 미미 |

## 1단계: 무료 조합의 한계 (케이스 1~2)

**케이스 1: 전부 무료로.** 임베딩은 Ollama의 `nomic-embed-text`, 생성은 `qwen2.5:14b-instruct-q4_K_M`, 데이터는 QnA 160개.

- 임베딩에 1시간 이상. 매우 느림.
- 답변 정확도 40% 이하.

무료 임베딩 모델이 한국어에 약했고, 로컬 하드웨어도 받쳐주지 않았다. 이 구성으로는 상용 서비스에 필요한 속도와 정확도를 맞추기 어려웠다.

**케이스 2: 임베딩만 유료로.** 생성 모델은 그대로 두고 임베딩만 OpenAI `text-embedding-3-large`로 교체했다. 변수는 임베딩 하나뿐.

| 지표 | 케이스 1 | 케이스 2 |
|---|---|---|
| 정확도 | 40% 이하 | 70% 이상 |
| 임베딩 속도 | 1시간+ | 1분 이하 |

정확도는 30%p 올랐고 속도는 60배 빨라졌다. 다만 Vector DB와 Graph DB를 함께 구축했을 때 Graph 응집도가 매우 낮았다. 임베딩 모델 단독으로는 의미적 연관관계를 못 뽑고, 카테고리 기반 단순 연결만으로는 지식 그래프 품질이 떨어진다는 첫 신호였다.

## 2단계: 자체 스택 전환과 비용 폭탄 (케이스 3~4)

**케이스 3: Milvus + Neo4j로 마이그레이션.** 임베딩 `text-embedding-3-large`, 생성 `gpt-4o-mini`. 여기서 가장 비싼 교훈을 얻었다.

- 임베딩에만 1시간 10분 넘게 걸렸다. 완주는 했지만 실용성이 없다고 판단해 정확도를 재기 전에 멈췄다.
- 임베딩 설정을 잘못 잡자 내부적으로 호출이 반복됐다. 예상 $0.01 수준이던 비용은 실제 $22까지 올라 약 2,200배 차이가 났다.

중복 호출과 재시도 설정이 비용을 키웠다.

- 데이터 처리 로직 결함으로 **중복 API 호출**
- 배치 처리 미구현 → 개별 호출 과다
- 에러 핸들링 부재 → 무한 재시도
- 임베딩 캐싱 미적용

**케이스 4: 파이프라인 최적화.** 100개 단위 배치 임베딩을 구현하고, Vector DB를 Qdrant로 경량화했다.

| 지표 | 케이스 3 | 케이스 4 |
|---|---|---|
| 임베딩 속도 | 1시간 10분+ | 30초 이내 |
| 정확도 | 미측정 | 85% 이상 |
| 비용 | $22 | $0.1 미만 |

같은 모델과 데이터로 속도가 140배 빨라졌고 비용도 정상 범위로 돌아왔다. 두 케이스를 비교해보니 모델 교체 없이 데이터 처리 방식만 바꿔도 비용과 속도를 개선할 수 있었다.

## 3단계: 지식 그래프 품질과의 싸움 (케이스 5)

**케이스 5-1: Neo4j 카테고리 기반 관계.** Qdrant(Vector 검색) + Neo4j(관계 검색) 하이브리드로 구성해 두 종류의 관계를 넣었다.

- `BELONGS_TO`: QnA → 카테고리
- `SIMILAR_TO`: 임베딩 유사도 0.7 이상

정확도는 90% 이상으로 유지됐지만 Graph 응집도는 여전히 낮았다. 카테고리 간 유사성이 높은 데이터가 부족했고, 카테고리 기반 관계만으로는 QnA 텍스트 내부의 실제 개념 관계를 담지 못했다.

**케이스 5-2: Vector DB만 교체 (Qdrant → Milvus).** Milvus의 확장성·고급 기능을 검증하려 Vector DB만 바꿔봤다.

속도와 정확도 모두 차이가 없었다. 문서 1건에서 뽑은 수백~900개 QnA라는 이 규모에선 Vector DB 선택이 병목이 아니었다(대규모에선 다를 수 있다). Graph 관계의 품질을 개선하려면 언어학적 특징을 이용한 관계 추출이 필요해 보였다.

## 4단계: 대화 맥락 붙이기 (케이스 6)

연속된 질문에서 이전 발화 맥락이 사라져 답변 품질이 떨어졌다. 케이스 6에서는 [mem0](https://github.com/mem0ai/mem0) 메모리 라이브러리를 통합해 대화 세션별로 이력을 관리했다.

- 대화 이력 기반 맥락 유지 가능
- 반복 질문 시 토큰 소비 감소
- 연속 대화에서 자연스러운 응답 확인

mem0는 채팅 이력을 압축된 메모리로 관리해 토큰과 지연을 줄이는 걸 지향하는데, 우리가 실제로 확인한 건 그중 토큰 소비 감소였다.

## 5단계: 형태소 삼중항이라는 마지막 시도 (케이스 7)

카테고리 관계로는 응집도가 나오지 않아 케이스 7에서 언어학적 관계를 직접 뽑기로 했다. [KoNLPy](https://konlpy.org/)의 Okt(Open Korean Text) 형태소 분석기로 QnA 텍스트에서 `주어·서술어 → 목적어` 형태의 삼중항을 자동 추출해 Entity 관계로 맵핑했다. 데이터는 교육 도메인 QnA 887개.

실제 단어 간 관계를 이용하면 지식 그래프의 응집도가 높아질 것으로 예상했다. 결과는 달랐다.

| 검색 방식 | 점수 범위 | 답변 기여 |
|---|---|---|
| Vector + `SIMILAR_TO` (임베딩 유사도) | 0.7 ~ 0.9 | 높음 |
| Graph Entity (형태소 삼중항) | 상대적으로 낮음 | 미미 |

Entity 간 의미적 관계는 답변 생성에 거의 기여하지 못했다. Vector 검색 + `SIMILAR_TO`만으로 충분한 결과가 나왔고 Entity 기반 Graph DB의 효과는 미미했다.

Okt는 속도를 우선한 분석기라 형태소 분석 품질이 상대적으로 낮다고 알려져 있다. 그렇게 뽑힌 삼중항이 만든 Entity 관계가 임베딩 유사도를 이기기는 어려웠을 것이다.

## 이 데이터에서는 지식 그래프의 효과가 작았다

일곱 케이스를 거치며 유료 임베딩과 배치 처리는 효과를 확인했다. 반면 지식 그래프를 추가했을 때 얻은 이득은 작았다.

실험 범위에서 내린 판단은 다음과 같다.

- **임베딩 모델**: 무료 조합은 정확도와 속도 모두 부족했다. 유료 임베딩으로 바꾼 뒤 두 지표가 개선됐다.
- **비용 방어**: 배치 처리, 캐싱, 에러 핸들링이 필요했다. 이를 빠뜨린 케이스에서는 비용이 $22까지 올랐다.
- **Vector DB**: 문서 1건·QnA 수백~900개 규모에서는 제품을 바꿔도 성능 차이가 없었다.
- **지식 그래프**: 카테고리·형태소 삼중항 수준의 관계로는 우리 QnA 데이터에서 효과를 확인하지 못했다. Entity 그래프를 추가하기 전에 데이터에 충분한 관계가 있는지 확인할 필요가 있었다.

지식 그래프 자체의 효용을 부정할 수 있는 실험은 아니다. 다만 이번 데이터와 관계 추출 방식에서는 기대했던 효과가 나오지 않았다.
