"그거"가 예약 취소라는 걸 사람은 앞 대화로 안다. 그런데 챗봇은 질문을 하나씩 따로 받아서, "그거 어떻게"만 보고는 뭘 묻는지 모른다. 방금처럼 엉뚱하게 결제 취소를 안내하는 이유다. 앞 대화를 이용해 대명사를 풀고 사용자가 자주 찾는 정보까지 기억하게 하려고 메모리 레이어를 붙이기로 했다.

## 대화의 핵심 정보를 벡터로 저장하는 mem0

후보는 [memori](https://discuss.pytorch.kr/t/memori-llm-ai-sql/8922)와 [mem0](https://docs.mem0.ai/) 둘이었다. 둘 다 대화에서 핵심 사실(Fact)을 뽑아 저장하는 오픈소스 메모리 레이어다. 갈리는 건 저장 방식이다. memori는 관계형 DB(SQL)에 넣고, mem0는 벡터로 넣는다.

mem0는 대화에서 LLM이 뽑은 핵심 사실(Fact)을 저장한다. 예를 들면 "예약 취소는 마이페이지에서 한다" 같은 정보다. 대화가 길어져도 추출한 Fact 수십 개만 남기고, 새 질문이 오면 관련 Fact를 찾아 LLM에 함께 넣어준다.

필요했던 기능은 대화 맥락으로 대명사를 풀고("그거" → "예약 취소") 사용자 프로파일을 기억하는 것이었다. RAG 검색에 이미 Milvus를 쓰고 있어서 벡터 방식인 mem0를 같은 스택에 붙이기도 쉬웠다. 메모리 저장소도 Milvus로 정했다.

기능 자체는 금방 붙었다. 시간을 잡아먹은 건 mem0가 함께 설치한 라이브러리였다. 처음에는 `import`가 실패했고, 그다음에는 `delete`가 예상과 다르게 동작했다.

## qdrant와 pymilvus의 protobuf가 import에서 충돌했다

mem0를 `import` 하는 순간 protobuf 디스크립터 충돌로 프로세스가 종료됐다.

protobuf는 데이터 형식을 미리 정의해두는 도구다(구글이 만들었고, 많은 라이브러리가 내부 통신에 쓴다). 프로그램이 시작할 때 이 형식 정의 파일(`.proto`)을 **전역 목록에 파일명으로 하나씩** 등록하는데, 같은 파일명이 두 번 등록되려 하면 "이미 있다"며 거부한다.

하필 `qdrant-client`와 `pymilvus`가 둘 다 `common.proto`라는 같은 이름의 정의를 들고 있었다. 한 프로세스에서 같이 로드되니 뒤에 온 쪽이 "A file with this name is already in the pool"이라며 죽었다. 에러가 물고 늘어진 `_POINTID`는 qdrant 쪽 정의의 심볼이었다.

우리는 벡터스토어로 Milvus만 썼지만, mem0가 `import` 과정에서 `qdrant_client`까지 불러왔다. 이때 qdrant의 proto가 pymilvus proto와 충돌했다.

흔한 해법부터 시도했다. `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python` 환경변수로 순수 파이썬 구현으로 바꾸는 방법인데, 우리 버전 조합에선 `_POINTID` 에러가 안 풀렸다.

충돌을 피하려고 **mem0를 import 하기 전에 `qdrant_client`를 stub 모듈로 선등록**해 해당 proto가 로드되지 않게 했다. 단 빈 모듈만 넣으면 mem0가 `from qdrant_client import QdrantClient` 하다가 `ImportError`가 난다. mem0가 참조하는 이름(`QdrantClient`, `models`)만 빈 껍데기로 채워두면 import는 통과하면서 실제 proto는 올라오지 않는다.

<details>
<summary>stub 선등록 (개념 최소 예제)</summary>

```python
import sys, types

def stub_qdrant_client():
    # mem0가 import 시 qdrant_client를 끌어온다. 그 proto(common.proto)가
    # pymilvus proto와 파일명·심볼(_POINTID)이 겹쳐 전역 풀에서 충돌한다.
    # Milvus만 쓰므로, 실제 qdrant_client 대신 빈 stub을 먼저 등록해 막는다.
    if "qdrant_client" in sys.modules:
        return
    stub = types.ModuleType("qdrant_client")
    stub.QdrantClient = type("QdrantClient", (), {})       # mem0 import가 찾는 이름만 채운다
    stub.models = types.ModuleType("qdrant_client.models")
    sys.modules["qdrant_client"] = stub
    sys.modules["qdrant_client.models"] = stub.models

stub_qdrant_client()
from mem0 import Memory  # 이제 qdrant proto가 안 올라와 충돌이 안 난다
```

</details>

정공법은 protobuf 패키징을 고치거나 버전을 맞추는 것이지만, 우리 쪽에서 손댈 수 있는 범위가 아니었다. 안 쓰는 벡터스토어를 로드조차 안 하게 막는 게 가장 확실했다.

덧붙이면, qdrant도 이 충돌 때문에 나중에 자기 `common.proto`를 `qdrant_common.proto`로 이름을 바꿨다. 버전에 묶인 문제라, 최신 조합에선 이 에러를 아예 안 볼 수도 있다. 우리가 겪은 건 그 전의 특정 버전 조합에서였다.

## delete_all이 필터를 무시하고 컬렉션을 비웠다

개발 중 한 사용자의 대화 메모리만 지우려고 `delete_all(user_id=...)`를 호출했는데, **테스트 컬렉션이 통째로 비었다.**

mem0 문서에는 `delete_all`이 user, agent, run, 메타데이터 기준으로 **필터해서 지운다**고 돼 있다. 실제 구현은 내부에서 `vector_store.reset()`을 호출했고, 이 메서드는 **컬렉션을 통째로 DROP하고 다시 만든다.** 필터는 적용되지 않았다.

같은 문제는 mem0 GitHub 이슈에도 올라와 있었다 ([#3928](https://github.com/mem0ai/mem0/issues/3928): "delete_all이 filter 대신 reset()을 호출해 전 유저 메모리를 지운다", [#3746](https://github.com/mem0ai/mem0/issues/3746)). 문서와 구현이 어긋난 알려진 버그였다.

`delete_all`은 빼고, 지울 메모리를 조회한 뒤 **개별 삭제를 반복**했다. 느리지만 테스트 컬렉션 전체가 비는 일은 없었다.

두 버그를 잡고 나니, 처음 목표대로 됐다. 이제 챗봇은 "그거"를 앞 대화로 풀어 예약 취소를 제대로 안내하고, 사용자 프로파일도 기억한다.

## 두 버그에서 확인한 것

- **의존성 추적**: Milvus만 사용해도 qdrant proto가 함께 로드됐다. `import`가 실패하면 직접 쓰는 코드뿐 아니라 라이브러리가 불러오는 의존성까지 확인해야 한다.
- **삭제 연산 검증**: 문서와 실제 구현은 다를 수 있다. 되돌리기 어려운 연산은 별도 테스트 데이터로 동작을 확인해야 한다. `delete_all` 한 줄이 테스트 컬렉션을 통째로 지웠다.
- **이슈 트래커 확인**: 두 문제 모두 먼저 겪은 사용자가 이슈를 남겨뒀다. 원인을 찾기 전에 같은 버전의 이슈가 있는지 확인하면 시간을 줄일 수 있다.
