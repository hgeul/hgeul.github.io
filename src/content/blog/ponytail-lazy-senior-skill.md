AI 코딩 에이전트를 쓰다 보면 이런 불만이 쌓인다. 시키지도 않은 인터페이스를 만들고, 지금 구현체가 하나뿐인데 전략 패턴 깔고, 짧게 끝날 일을 계층으로 늘린다. 

마침 이런 불만을 해결해 준다는 스킬이 있길래 직접 적용해 봤다.
그런데 일부러 둔 추상화까지 걷어낼까 걱정됐다. 그래서 바로 적용하지 않고 모드만 바꿔 같은 기능을 여러 번 짜게 한 뒤 diff로 비교했다.

## ponytail이란?

ponytail은 [github.com/DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)에서 받는 오픈소스 스킬이다(제작자 Dietrich Gebert, MIT). 코딩 에이전트한테 "게으른 시니어 개발자"처럼 굴라고 시킨다. 여기서 게으르다는 건 안 해도 되는 일을 하지 않는다는 뜻이다. 핵심은 사다리(ladder)다. 코드를 짜기 전에 아래를 위에서부터 따져보고 먼저 걸리는 단에서 멈춘다.

1. 이게 있을 필요가 있나? (YAGNI) 없으면 건너뛴다.
2. 이미 코드베이스에 있나?
3. 표준 라이브러리로 되나?
4. 플랫폼 네이티브 기능으로 되나?
5. 이미 깔린 의존성으로 되나?
6. 한 줄로 되나?
7. 그제서야 동작하는 최소 코드.

모드는 세 가지다.

| 모드 | 동작 |
|---|---|
| **lite** | 관례대로 짓되, 더 게으른 대안을 한 줄로 제시. 선택은 사람이 |
| **full** | 사다리 강제. 가장 짧은 diff. 기본값 |
| **ultra** | YAGNI 극단. 추가보다 삭제 |

이 글에서는 실무에서 자주 쓰는 full과 lite만 비교했다. ultra는 뺐다.

여기 단서가 하나 있다. ponytail에는 "게으르면 안 되는 것"도 박혀 있다. 신뢰 경계 검증(trust-boundary validation), 데이터 유실 처리, 보안, 접근성은 단순화한다고 절대 못 지운다. 


<details>
<summary>스킬 파일(SKILL.md) 안에는 뭐가 들어 있나</summary>

스킬이 에이전트한테 실제로 주는 지시가 이렇다. ([원문 SKILL.md](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md))

- **한 줄 모토**: *"The best code is the code you never wrote."* (안 쓴 코드가 최고의 코드)
- **사다리 방식**: 위 7단계를 코드 짜기 전에 순서대로 통과시킨다.
- **게으르면 안 되는 것**: 신뢰 경계의 입력 검증, 데이터 유실을 막는 예외 처리, 보안, 접근성 기본, 그리고 "명시적으로 요청된 것"은 단순화 대상에서 뺀다.
- **결과 표기 방식**: 뭔가를 건너뛸 때 그냥 지우는 게 아니라 `[코드] → skipped: [무엇을], add when [언제]` 꼴로 남기게 한다.

마지막 항목이 실험에서 본 `// lazy:` 주석의 정체다. 스킬이 "생략은 하되 흔적은 남겨라"라고 시키니까, full 모드의 단축이 리뷰에서 되돌릴 수 있는 형태로 남는 것이다.

</details>

## full은 필요한 코드까지 지우지 않았다

full 모드는 기능에 군더더기가 많을 때 코드를 많이 줄였고, 필요한 코드만 있는 경우에는 거의 손대지 않았다. lite 모드는 코드를 바꾸지 않고 더 단순한 방법만 제안했다.

## 실험 방식

모드 차이만 보려고 나머지 변수 세 가지를 고정했다.

1. **같은 스펙.** 세 변형(normal = ponytail off, lite, full)에 똑같은 기능 스펙을 준다. 그래야 결과 차이를 모드 때문이라고 볼 수 있다.
2. **같은 base 브랜치.** 세 변형을 같은 커밋에서 땄다. 실험 도중 메인이 움직이면 diff가 더러워지니 base 커밋을 고정했다.
3. **같은 에이전트·모델.** Claude Code에 Opus 4.7로 고정했다.

대상은 Java 백엔드(이벤트 루프 웹 프레임워크 + 액티브 레코드 ORM). 성격이 정반대인 기능 둘을 골랐다.

| 기능 | 성격 | 걷어낼 군더더기 |
|---|---|---|
| 예시 1 | 외부 호출 0, 순수 DB 읽기 | 많음 |
| 예시 2 | 외부 API 호출에 묶임 | 거의 없음 |

## 예시 1: 군더더기가 많은 기능 (순수 DB 읽기)

**스펙:** 어떤 명령의 처리 상태를 ID로 다시 조회하는 API. DB 로그를 읽어 `{ id, status, errorType }`를 돌려준다. 외부 호출 0. 단, 남의 ID로는 못 보게 소유자 격리 검증은 필수.

| 모드 | 파일 | 추가 줄 | 비고 |
|---|---|---|---|
| normal | 7 | +177 | 풀 컨벤션 기준선 |
| lite | 7 | +177 | normal과 코드 100% 동일 |
| full | 4 | +99 | 파일 −43%, 줄 −44% |

full은 normal이 만든 것 중 세 덩어리를 통째로 지웠다.

- 외부 호출용 서비스 인터페이스에 추가한 메서드
- 그 인터페이스의 구현체 코드
- 이 케이스 전용으로 신설한 도메인 에러 코드

외부 호출이 하나도 없어서 추상화 계층을 거칠 이유가 없었다. normal은 관례대로 컨트롤러 → 서비스 → 인터페이스 → DB로 내려갔지만, full은 서비스와 인터페이스를 빼고 컨트롤러에서 바로 조회했다.

<details>
<summary>full 모드가 짠 컨트롤러 (개념 최소 예제)</summary>

```java
// 순수 DB 읽기라 서비스 계층 없이 컨트롤러에서 직접 조회
var commandId = req.commandId();
if (commandId == null) return badRequest();

// lazy: 외부 호출이 0이라 서비스로 안 올림. 외부 API 생기면 그때 승격.
//       소유자 격리는 WHERE 조건으로 유지.
var cmd = db.find(Command.class)
        .where().eq("id", commandId)
        .eq("userId", currentUserId)   // 남의 명령 차단
        .findOneOrNull();
if (cmd == null) return notFound();

return ok(new CommandStatus(cmd.id(), cmd.status(), cmd.errorType()));
```

</details>

여기서 full이 한 일을 뜯어보면 이렇다.

- **컨벤션은 깼다.** "컨트롤러는 서비스를 거친다"를 어기고 직접 쿼리했다.
- **숨기진 않았다.** `// lazy:` 주석으로 단축임을 표시하고 승격 경로를 남겼다.
- **안전은 지켰다.** 소유자 격리(`user.id` 조건)는 그대로 뒀다.

리뷰에서는 이 기능이 컨벤션을 깨고 직접 조회해도 되는지 판단하면 된다. 소유자 격리 조건은 두 구현 모두 유지했다.

## 예시 2: 군더더기가 없는 기능 (외부 API 결합)

**스펙:** 기존 조회 API에 "한 종류만 좁혀서 조회"하는 옵션 필터 추가. 
필터가 있으면 외부 API에 그 종류만 요청해 호출 부하를 줄인다. 필터 없으면 기존 전체 조회(하위호환).

| 모드 | 파일 | 추가/삭제 | 비고 |
|---|---|---|---|
| normal | 5 | +50 / −10 | 기준선 |
| lite | 5 | +50 / −10 | normal과 코드 100% 동일 |
| full | 5 | +43 / −10 | 파일 제거 0, 줄 −7 (사실상 0) |

예시 2에서 full이 줄인 코드는 7줄뿐이었다. normal과 비교해 바뀐 파일은 2개였고 사라진 파일은 없다. 분기 하나를 삼항으로 줄이고 주석을 정리한 게 전부다.

<details>
<summary>normal vs full 코드 (개념 최소 예제)</summary>

```java
// normal
List<String> buildTypeFilter(DeviceType filter) {
    var types = new ArrayList<String>();
    if (filter != null) {
        types.add(filter.code());
    } else {
        types.addAll(List.of("a", "b", "c" /* ... 전체 종류 ... */));
    }
    return types;
}

// full: 기능은 동일, 표현만 약간 간결
private static final List<String> ALL_TYPES = List.of("a", "b", "c" /* ... */);

List<String> buildTypeFilter(DeviceType filter) {
    return filter == null ? ALL_TYPES : List.of(filter.code());
}
```

</details>

왜 이번엔 못 걷어냈나. 이 기능은 외부 호출 자체를 좁히는 일이라, 건드리는 코드가 전부 꼭 필요한 것들이다.

- DTO 필터 필드: 필수
- 인터페이스 시그니처 변경: 필수 (이 인터페이스는 실제로 외부 호출을 라우팅한다)
- 컨트롤러 가드: 필수

예시 2의 코드는 외부 호출에 필요해서 full도 그대로 뒀다.

## 군더더기가 있을 때만 코드가 줄었다

두 예시에서 full이 줄인 코드의 양은 크게 달랐다.

| | 예시 1 (순수 읽기) | 예시 2 (외부API 결합) |
|---|---|---|
| full 파일 수 | 7 → 4 (3개 제거) | 5 → 5 (제거 0) |
| full 줄 절감 | −44% | 약 0% |
| full이 한 일 | 인터페이스·서비스·전용에러 제거 | 거의 그대로 |
| 왜 | 외부 호출 0인데 추상화 경유 = 순수 군더더기 | 인터페이스가 실제로 외부 호출 라우팅 → 제거 불가 |

full이 얼마나 줄이는지는 그 기능에 낀 군더더기 양에 달렸다.

## 저자 공식 벤치마크와 비교하면

ponytail 저자도 "측정이 과장 아니냐"는 비판을 받고 벤치마크를 다시 했는데, 결과가 이번 실험이랑 비슷했다.

- **초기 단발(single-shot) 측정**: 코드 80~94% 감소. 그런데 저자 본인이 *"이 수치는 비교 대상(스킬 없는 챗봇)이 옵션이랑 설명을 길게 늘어놔서 부풀려진 것"*이라고 정정했다.
- **다시 한 에이전트 벤치마크** (2026-06-18): 실제 공개 repo `tiangolo/full-stack-fastapi-template`을 Claude Code 헤드리스(Haiku 4.5)로 고치고, LOC = `git diff` 추가 줄로 쟀다. 비교 대상은 스킬만 끈 같은 에이전트다.
  - 오버빌드를 유발하는 기능 12개: 평균 **−54%** (불가피한 CRUD는 0%, 날짜 선택기는 −94%까지 폭이 컸다)
  - 이미 최소화된 코드 6개: **−5%** (사실상 그대로)
  - 곁다리 지표: 토큰 −22%, 비용 −20%, 시간 −27%
  - 안전: ponytail은 20번 돌려 100% 유지. 대조군 `yagni-oneliner`만 path-traversal 가드를 한 번 빠뜨려 95%였고, ponytail은 그 3줄을 지켰다.

저자 벤치마크랑 이번 실험 수치를 비교하면 이렇다.

| | 저자 에이전트 벤치마크 | 이번 실험 |
|---|---|---|
| 오버빌드 함정 있는 기능 | 평균 −54% (0 ~ −94%) | 예시 1: −44% |
| 이미 최소화된 코드 | −5% (wash) | 예시 2: ≈0% |
| 안전성 | 100% 유지 | 침해 0 |
| 모델 | Haiku 4.5 | Opus 4.7 |
| 측정 방식 | `git diff`, 스킬 유무만 변수 | 동일 |

코드베이스도 기능도 다르고 모델까지 다른데, 결과는 비슷했다. 이번 −44%도 저자의 오버빌드 범위(0 ~ −94%, 평균 −54%) 안에 든다. 저자가 "옛 80~94%는 부풀려졌다"고 인정한 것도 같은 얘기다.

## lite 모드: 코드 변경 없는 안전한 대안

두 실험 다 normal이랑 lite의 diff가 비어 있었다. lite는 관례대로 꽉 짜고(normal과 똑같이), 더 게으른 길은 적용 안 하고 말로만 제안했다. 이런 식이다.

> "이건 순수 DB 읽기라 서비스 계층을 거치지 않고 직접 조회할 수도 있습니다. 구조 일관성을 위해 일단 관례대로 뒀습니다. 원하시면 걷어내죠."

lite는 normal과 같은 코드를 만들고 단순화 방안만 제안했다. 구조는 바뀌지 않으며 제안을 적용할지는 사용자가 정한다.

## 새 코드에는 full, 기존 구조에는 lite

두 모드의 차이는 안전 경계를 건드리느냐가 아니라, 아직 필요하지 않은 추상화를 어디까지 걷어내느냐다.

- **아직 패턴에 안 묶인 새 유틸, 일회성 로직, 작은 버그픽스** → `full`. 걷어낼 군더더기가 많고 컨벤션 충돌이 적다.
- **확립된 의무 패턴을 따라야 하는 코드(새 컨트롤러·엔티티 등)** → `lite`. 구조를 안 건드리고 대안만 받아 직접 판단한다. full은 자꾸 추상화를 걷어내려 하니까.
- **"구조 무시할까 봐" 걱정될 때** → 그냥 `lite`. 코드는 동일, 위험 0.

full은 컨벤션을 깰 때 `// lazy:` 주석으로 줄인 범위와 되돌리는 방법을 남긴다. 이 실험에서는 주석과 diff를 보고 단축을 유지하거나 되돌릴 수 있었다.
