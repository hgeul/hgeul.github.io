<h2>2. 벡터와 거리: 기본 개념</h2>
<div class="two-col">
<div>
<h3>2.1 벡터란?</h3>
<p>
벡터는 그냥 숫자들의 배열입니다. 예를 들어:
</p>

```
[0.2, -0.5, 0.8]   # 3차원 벡터
[0.01, 1.2, -0.7, 0.3, ...]   # 768차원, 1536차원 같은 고차원 벡터
```

<p>
LLM 임베딩도 결국 이런 벡터입니다.  
“문장의 의미, 톤, 주제” 같은 정보를 여러 숫자로 쪼개어 표현한 것이라고 보면 됩니다.
</p>

<h3>2.2 거리란?</h3>
<p>
벡터끼리의 <strong>비슷함/다름</strong>을 판단하려면,  
“두 점이 얼마나 떨어져 있는가?”를 알아야 합니다.  
이걸 <strong>거리(distance)</strong>라고 부릅니다.
</p>

<h2>3. 유클리드 거리와 코사인 유사도</h2>

<h3>3.1 유클리드 거리 (Euclidean Distance)</h3>
<span class="pill">거리 기반</span>
<p>
우리가 학교에서 배운 “피타고라스 정리” 그대로입니다.  
두 점 사이의 실제 직선 거리를 잽니다.
</p>

```
예) 2차원 벡터 (x1, y1), (x2, y2)

유클리드 거리 ≈ sqrt( (x1 - x2)² + (y1 - y2)² )
```

<ul>
<li>값이 <strong>작을수록</strong> 두 벡터가 가깝다.</li>
<li>크기(길이)와 방향이 모두 영향을 미친다.</li>
</ul>

<h3>3.2 코사인 유사도 (Cosine Similarity)</h3>
<span class="pill">각도 기반</span>
<p>
코사인 유사도는 “두 벡터가 <strong>어느 방향을 보고 있는지</strong>”에 집중합니다.
길이는 크게 신경 쓰지 않고, 두 벡터 사이의 <strong>각도</strong>만 봅니다.
</p>

```
코사인 유사도 = -1 ~ 1 사이의 값
1에 가까울수록 → 방향이 거의 같다 (아주 비슷)
0에 가까울수록 → 서로 직각 (관련성 낮음)
-1에 가까울수록 → 완전히 반대 방향
```

<div class="two-col">
<div>
<h4>언제 코사인 유사도를 쓰나?</h4>
<ul>
<li>문장 임베딩, 문서 임베딩처럼 <strong>길이보다는 방향</strong>이 중요할 때</li>
<li>값의 스케일 차이가 커도, “의미적 방향”을 기준으로 비교하고 싶을 때</li>
</ul>
</div>
<div>
<h4>언제 유클리드 거리를 쓰나?</h4>
<ul>
<li>벡터의 <strong>절대적인 값 차이</strong>가 중요한 경우</li>
<li>이미 잘 정규화된 공간에서, 물리적인 거리감에 가까운 비교를 원할 때</li>
</ul>
</div>
</div>

<h2>4. ANN (Approximate Nearest Neighbor)</h2>
<span class="pill">근사 최근접 탐색</span>
<p>
<strong>Nearest Neighbor</strong>는 말 그대로 “가장 가까운 이웃”입니다.  
하지만 데이터가 수백만·수억 개가 되면, 모든 점을 하나씩 비교하는 것은 너무 느립니다.
</p>
<p>
그래서 등장하는 개념이 바로 <strong>ANN(Approximate Nearest Neighbor)</strong> 입니다.
</p>
<ul>
<li><strong>정확한 1등</strong> 대신, 거의 1등과 비슷한 후보를 찾는다.</li>
<li>대신 속도는 <strong>훨씬 빠르고</strong>, 메모리도 <strong>훨씬 적게</strong> 쓴다.</li>
<li>Milvus, Qdrant, Pinecone 등 대부분의 벡터 DB는 ANN을 기본으로 사용한다.</li>
</ul>
<div class="note">
RAG 시스템에서 “최신 답변 5개 정도”만 잘 찾으면 되는 상황에서는  
<strong>ANN으로 충분</strong>하고, 오히려 필수에 가깝습니다.
</div>

<h2>5. HNSW: 그래프를 타고 가는 검색</h2>
<span class="pill">HNSW</span>
<span class="pill-outline">Hierarchical Navigable Small World</span>

<p>
HNSW는 “그래프를 타고 내려가면서 가까운 점을 찾는 방식”입니다.
</p>

<h3>5.1 핵심 아이디어</h3>
<ul>
<li>데이터 포인트들을 <strong>그래프 형태</strong>로 연결한다.</li>
<li>위로 갈수록 <strong>대충 보기 위한 층(상위 레벨)</strong>, 아래로 갈수록 <strong>자세히 보기 위한 층(하위 레벨)</strong>이 있다.</li>
<li>검색할 때는 <strong>위층에서 시작해서</strong>, 점점 <strong>아래층으로 내려오면서</strong> 가까운 이웃을 좁혀간다.</li>
</ul>

<ul>

<li>Qdrant, Milvus 둘 다 HNSW를 많이 사용</li>

<h3>6.2 PQ (Product Quantization)</h3>
<p>
PQ는 벡터를 <strong>압축해서 저장</strong>하는 기술입니다.
</p>
<ul>
<li>원래 벡터는 float 숫자들이라서 메모리를 많이 차지한다.</li>
<li>PQ는 벡터를 여러 조각으로 나눈 뒤, <strong>각 조각을 코드북(codebook) 인덱스로 치환</strong>한다.</li>
<li>이렇게 하면 “정확한 값”은 조금 잃지만, <strong>메모리는 크게 줄고 검색 속도는 올라간다.</strong></li>
</ul>

<h3>6.3 IVF-PQ를 한 문장으로</h3>
<p>
<strong>IVF</strong>로 “어느 동네를 볼지”를 먼저 정하고,<br/>
<strong>PQ</strong>로 “그 동네 안의 벡터들을 압축해서 빠르게 찾는” 방식입니다.
</p>

<td>전망대에서 대충 방향 잡고, 근처 골목으로 내려가서 자세히 찾는 느낌</td>
</tr>
<tr>
<td>IVF-PQ</td>
<td>클러스터링 + 압축 기반 검색</td>
<td>도시를 여러 구역으로 나누고(IVF), 각 집 주소를 짧게 코딩해두고(PQ) 찾는 느낌</td>
</tr>
<tr>
<td>RAG에서 벡터</td>
<td>질문과 문서를 같은 공간에 두고 “가까운 문서”를 찾아주는 역할</td>
<td>질문과 가장 잘 맞는 자료를, 미리 정리해둔 책꽂이에서 골라오는 사서</td>
</tr>
<tr>
<td>mem0 + Milvus</td>
<td>대화 기록과 사용자 정보를 “기억 벡터”로 저장·검색</td>
<td>사용자 히스토리를 대신 기억해 주는 <strong>똑똑한 비서 + 검색 엔진</strong> 조합</td>
</tr>
</tbody>
</table>
<div class="note">
Milvus, Qdrant에서 인덱스 타입을 선택할 때  
<strong>“HNSW vs IVF-PQ”</strong> 정도만 구분해도 실무에서는 크게 도움이 됩니다.
</div>

<h2>8. Milvus / Qdrant 설정을 볼 때 읽는 법</h2>
<p>
실제 벡터 DB 설정에서 이런 옵션들을 볼 수 있습니다:
</p>

```
# 예시 (개념용 의사 코드)

index_type: "HNSW"
metric_type: "COSINE"

# 또는

index_type: "IVF_PQ"
metric_type: "L2"  # L2 = 유클리드 거리
```

<ul>
<li>`metric_type: "COSINE"` → <strong>코사인 유사도</strong>로 벡터 비교</li>
<li>`metric_type: "L2"` → <strong>유클리드 거리</strong>로 벡터 비교</li>
<li>`index_type: "HNSW"` → 그래프 기반 ANN</li>
<li>`index_type: "IVF_PQ"` → 클러스터링 + 압축 기반 ANN</li>
</ul>
<div class="note">
LLM 임베딩 기반 RAG에서는  
<strong>코사인 유사도 + HNSW</strong> 조합이 많이 쓰이고,  
아주 큰 규모/저비용 저장이 필요할 때 <strong>IVF-PQ</strong>를 고려합니다.
</div>

<h2>9. RAG에서 벡터가 하는 일</h2>
<span class="pill">RAG 파이프라인</span>
<span class="pill-outline">Retrieval Augmented Generation</span>

<h3>9.1 RAG를 한 줄로 요약하면</h3>
<p>
RAG는 이렇게 동작합니다:
</p>
<ol>
<li>문서들을 잘게 쪼개서(<strong>chunk</strong>) 저장해 두고,</li>
<li>각 chunk를 임베딩 모델로 <strong>벡터로 변환</strong>하여 벡터 DB에 넣어 두고,</li>
<li>사용자가 질문하면, 질문도 <strong>같은 모델</strong>로 벡터로 만든 뒤,</li>
<li>벡터 DB에서 <strong>“가장 비슷한 chunk 벡터”</strong>들을 찾아오고,</li>
<li>그 chunk 텍스트를 LLM에게 함께 넘겨서 <strong>답변을 생성</strong>하게 합니다.</li>
</ol>
<div class="note">
핵심은 “질문”과 “문서 조각”을 <strong>같은 벡터 공간에 올려두고</strong>,  
그 안에서 <strong>가까운 것끼리 매칭</strong>한다는 점입니다.
</div>

</div>

<h2>10. mem0와 Milvus: 벡터 메모리 레이어 예시</h2>
<span class="pill">mem0</span>
<span class="pill">Milvus</span>
<span class="pill-outline">장기 메모리 + 벡터 DB</span>

<div class="two-col">
<div>
<h3>10.1 mem0는 무엇을 하고, Milvus는 어디에 쓰일까?</h3>
<p>
<strong>mem0</strong>는 LLM용 <strong>“장기 메모리 레이어”</strong>라고 볼 수 있습니다.
</p>
<ul>
<li>대화 내용, 사용자 정보, 과거 요청/응답 등을 <strong>“기억”</strong>으로 관리</li>
<li>이 기억들을 텍스트 그대로만 두지 않고, <strong>임베딩 벡터</strong>로도 만들어 둠</li>
<li>“예전에 한 말”과 <strong>비슷한 상황이 오면</strong>, 그 기억을 다시 찾아서 LLM에 공급</li>
</ul>
<p>
이때, <strong>“기억 벡터를 저장하고 빨리 찾는 역할”</strong>을 Milvus가 담당할 수 있습니다.
</p>
<div class="note">
정리하면:  
<strong>mem0 = 어떤 것을 기억할지/어떻게 요약·병합할지 결정</strong>  
<strong>Milvus = 그 기억들을 벡터 공간에서 빠르게 검색</strong>
</div>
</div>
<div>
<h3>10.2 구성 예시 코드 (개념용)</h3>
<p>mem0 설정에서 Milvus를 벡터 스토어로 지정하는 예시는 다음과 같습니다:</p>

```
from mem0 import Memory

config = {
    "vector_store": {
        "provider": "milvus",
        "config": {
            "collection_name": "mem0_memory",
            "embedding_model_dims": 1536,
            "url": "http://localhost:19530",   # Milvus 서버 주소(기본 포트 19530)
            "db_name": "mem0_db",
        }
    }
}

memory = Memory.from_config(config)
```

<ul>
<li>`provider: "milvus"` → 벡터 검색을 Milvus에게 맡기겠다는 의미</li>
<li>`collection_name` → “기억”을 저장할 Milvus 컬렉션 이름</li>
<li>`embedding_model_dims` → 사용하는 임베딩 모델의 차원 수</li>
</ul>
</div>
</div>

<h2>11. 한 문장씩 다시 정리</h2>
<ul>
<li><strong>유클리드 거리</strong> → 점과 점 사이의 직선 거리</li>
<li><strong>코사인 유사도</strong> → 벡터 방향의 비슷함 (각도)</li>
<li><strong>ANN</strong> → “거의 가장 가까운 것”을 빠르게 찾는 전략</li>
<li><strong>HNSW</strong> → 그래프를 여러 층으로 쌓아 위에서 아래로 내려가며 탐색</li>
<li><strong>IVF-PQ</strong> → 클러스터링 후, 그 안을 압축해서 빠르게 찾기</li>
<li><strong>RAG에서 벡터</strong> → 질문과 문서를 같은 벡터 공간에 올려두고, <strong>“서로 가까운 것끼리 매칭”</strong>하는 기술</li>
<li><strong>mem0 + Milvus</strong> → 대화/사용자 히스토리를 벡터로 저장·검색해서, <strong>LLM에게 “장기 기억”을 붙여주는 구조</strong></li>
</ul>
<div class="note">
앞으로 Milvus / Qdrant / RAG / mem0 관련 문서를 볼 때,
“아, 이건 결국 <strong>어떤 임베딩 + 어떤 거리(metric) + 어떤 ANN 인덱스 + 어떤 메모리 레이어</strong>를 쓰는지 이야기구나”
정도만 떠올려도 훨씬 편하게 이해하실 수 있을 것입니다.
</div>
