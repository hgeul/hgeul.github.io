RAG 스택을 굴리다 보면 벡터 DB 설정 파일을 계속 마주친다. `index_type: HNSW`, `metric_type: COSINE`, 어떤 케이스에선 `IVF_PQ`. 그때마다 "이게 정확히 뭐 하는 옵션이더라" 하고 멈칫했다. 매번 문서를 다시 뒤지기 싫어서 한 번 정리해 뒀다. ([RAG 회고글](/blog/rag-pipeline-graphdb-lessons)에서 결국 벡터 검색 + 유사도로 충분했다고 적었는데, 그 벡터 검색이 안에서 뭘 하는지가 이 글이다.)

수학적으로 완벽한 설명은 아니다. 설정 창에서 용어를 보고 "아 이건 이런 거지" 하고 넘어갈 수 있는 정도의 직관이 목표다.

<h2>2. 벡터와 거리: 기본 개념</h2>
<div class="two-col">
<div>
<h3>2.1 벡터란</h3>
<p>
벡터는 그냥 숫자들의 배열이다. 예를 들면 이렇다.
</p>

```
[0.2, -0.5, 0.8]   # 3차원 벡터
[0.01, 1.2, -0.7, 0.3, ...]   # 768, 1536차원 같은 고차원 벡터
```

<p>
LLM 임베딩도 결국 이런 벡터다. 문장의 의미, 톤, 주제 같은 정보를 여러 숫자로 쪼개 표현한 것이라고 보면 된다.
</p>

<h3>2.2 거리란</h3>
<p>
벡터끼리 <strong>비슷한지 다른지</strong> 판단하려면 "두 점이 얼마나 떨어져 있나"를 알아야 한다. 이걸 <strong>거리(distance)</strong>라고 부른다.
</p>
</div>

<h2>3. 유클리드 거리와 코사인 유사도</h2>

<h3>3.1 유클리드 거리 (Euclidean Distance)</h3>
<span class="pill">거리 기반</span>
<p>
학교에서 배운 피타고라스 정리 그대로다. 두 점 사이의 실제 직선 거리를 잰다.
</p>

```
예) 2차원 벡터 (x1, y1), (x2, y2)

유클리드 거리 ≈ sqrt( (x1 - x2)² + (y1 - y2)² )
```

<ul>
<li>값이 <strong>작을수록</strong> 두 벡터가 가깝다.</li>
<li>크기(길이)와 방향이 모두 영향을 준다.</li>
</ul>

<h3>3.2 코사인 유사도 (Cosine Similarity)</h3>
<span class="pill">각도 기반</span>
<p>
코사인 유사도는 두 벡터가 <strong>어느 방향을 보고 있는지</strong>에 집중한다. 길이는 크게 신경 쓰지 않고 두 벡터 사이의 <strong>각도</strong>만 본다.
</p>

```
코사인 유사도 = -1 ~ 1 사이의 값
1에 가까울수록 → 방향이 거의 같다 (아주 비슷)
0에 가까울수록 → 서로 직각 (관련성 낮음)
-1에 가까울수록 → 완전히 반대 방향
```

<div class="two-col">
<div>
<h4>코사인 유사도를 쓸 때</h4>
<ul>
<li>문장·문서 임베딩처럼 <strong>길이보다 방향</strong>이 중요할 때</li>
<li>값의 스케일 차이가 커도 "의미적 방향"을 기준으로 비교하고 싶을 때</li>
</ul>
</div>
<div>
<h4>유클리드 거리를 쓸 때</h4>
<ul>
<li>벡터의 <strong>절대적인 값 차이</strong>가 중요할 때</li>
<li>이미 잘 정규화된 공간에서 물리적 거리감에 가까운 비교를 원할 때</li>
</ul>
</div>
</div>

<h2>4. ANN (Approximate Nearest Neighbor)</h2>
<span class="pill">근사 최근접 탐색</span>
<p>
Nearest Neighbor는 말 그대로 "가장 가까운 이웃"이다. 그런데 데이터가 수백만, 수억 개가 되면 모든 점을 하나씩 비교하는 건 너무 느리다. 그래서 나온 게 <strong>ANN(Approximate Nearest Neighbor)</strong>이다.
</p>
<ul>
<li><strong>정확한 1등</strong> 대신 거의 1등과 비슷한 후보를 찾는다.</li>
<li>대신 속도는 <strong>훨씬 빠르고</strong> 메모리도 <strong>훨씬 적게</strong> 쓴다.</li>
<li>Milvus, Qdrant, Pinecone 등 대부분의 벡터 DB가 ANN을 기본으로 쓴다.</li>
</ul>
<div class="note">
RAG에서 "관련 자료 5개 정도"만 잘 찾으면 되는 상황이라면 ANN으로 충분하다. 오히려 필수에 가깝다.
</div>

<h2>5. HNSW: 그래프를 타고 가는 검색</h2>
<span class="pill">HNSW</span>
<span class="pill-outline">Hierarchical Navigable Small World</span>

<p>
HNSW는 그래프를 타고 내려가면서 가까운 점을 찾는 방식이다.
</p>

<h3>5.1 핵심 아이디어</h3>
<ul>
<li>데이터 포인트들을 <strong>그래프 형태</strong>로 연결한다.</li>
<li>위로 갈수록 <strong>대충 보는 층(상위 레벨)</strong>, 아래로 갈수록 <strong>자세히 보는 층(하위 레벨)</strong>이다.</li>
<li>검색은 <strong>위층에서 시작해</strong> 점점 <strong>아래층으로 내려오며</strong> 가까운 이웃을 좁혀간다.</li>
</ul>

<h3>5.2 특징</h3>
<ul>
<li>읽기(검색) 속도가 아주 빠르고 정확도도 높은 편이다.</li>
<li>그래프 구조를 유지해야 해서 삽입·삭제에는 비용이 좀 든다.</li>
<li>Qdrant, Milvus 둘 다 HNSW를 많이 쓴다.</li>
</ul>

<h2>6. IVF-PQ: 클러스터링 + 압축</h2>
<span class="pill">IVF</span>
<span class="pill">PQ</span>

<h3>6.2 PQ (Product Quantization)</h3>
<p>
PQ는 벡터를 <strong>압축해 저장</strong>하는 기술이다.
</p>
<ul>
<li>원래 벡터는 float 숫자라서 메모리를 많이 차지한다.</li>
<li>PQ는 벡터를 여러 조각으로 나눈 뒤 <strong>각 조각을 코드북(codebook) 인덱스로 치환</strong>한다.</li>
<li>이러면 "정확한 값"은 조금 잃지만 <strong>메모리가 크게 줄고 검색 속도가 올라간다.</strong></li>
</ul>

<h3>6.3 IVF-PQ를 한 문장으로</h3>
<p>
<strong>IVF</strong>로 "어느 동네를 볼지"를 먼저 정하고,<br/>
<strong>PQ</strong>로 "그 동네 안의 벡터를 압축해 빠르게 찾는" 방식이다.
</p>

<h2>7. Milvus / Qdrant 설정을 읽는 법</h2>
<p>
실제 벡터 DB 설정에서 마주치는 옵션은 대략 이런 모양이다.
</p>

```
# 예시 (개념용 의사 코드)

index_type: "HNSW"
metric_type: "COSINE"

# 또는

index_type: "IVF_PQ"
metric_type: "L2"  # L2 = 유클리드 거리
```

<ul>
<li>`metric_type: "COSINE"` → <strong>코사인 유사도</strong>로 벡터 비교</li>
<li>`metric_type: "L2"` → <strong>유클리드 거리</strong>로 벡터 비교</li>
<li>`index_type: "HNSW"` → 그래프 기반 ANN</li>
<li>`index_type: "IVF_PQ"` → 클러스터링 + 압축 기반 ANN</li>
</ul>
<div class="note">
단, 벡터 DB마다 지원하는 인덱스가 다르다. <strong>IVF_PQ는 Milvus·Faiss 계열의 index_type</strong>이고, <strong>Qdrant는 ANN 인덱스가 HNSW 하나뿐</strong>이다. Qdrant에서 PQ(압축)는 별도 인덱스가 아니라 HNSW 위에 얹는 양자화 옵션으로 제공된다.
</div>
<div class="note">
LLM 임베딩 기반 RAG에서는 <strong>코사인 유사도 + HNSW</strong> 조합이 많이 쓰이고, 규모가 아주 크거나 저비용 저장이 필요할 때 <strong>IVF-PQ</strong>를 고려한다. 인덱스 타입 고를 때 <strong>"HNSW냐 IVF-PQ냐"</strong> 정도만 구분해도 실무에선 대개 충분하다.
</div>

<h2>8. RAG에서 벡터가 하는 일</h2>
<span class="pill">RAG 파이프라인</span>
<span class="pill-outline">Retrieval Augmented Generation</span>

<h3>8.1 RAG를 한 줄로</h3>
<p>
RAG는 이렇게 동작한다.
</p>
<ol>
<li>문서를 잘게 쪼개서(<strong>chunk</strong>) 저장하고,</li>
<li>각 chunk를 임베딩 모델로 <strong>벡터로 변환</strong>해 벡터 DB에 넣고,</li>
<li>사용자가 질문하면 질문도 <strong>같은 모델</strong>로 벡터로 만든 뒤,</li>
<li>벡터 DB에서 <strong>"가장 비슷한 chunk 벡터"</strong>를 찾아오고,</li>
<li>그 chunk 텍스트를 LLM에 함께 넘겨 <strong>답변을 생성</strong>하게 한다.</li>
</ol>
<div class="note">
핵심은 "질문"과 "문서 조각"을 <strong>같은 벡터 공간에 올려두고</strong> 그 안에서 <strong>가까운 것끼리 매칭</strong>한다는 점이다.
</div>

<h3>8.4 실무 선택 가이드</h3>
<ul>
<li>텍스트·문서 RAG → <strong>코사인 유사도 + HNSW</strong> 조합이 무난하고 많이 쓴다.</li>

</ul>

<h2>9. mem0 + Milvus: 벡터 메모리 레이어 예시</h2>
<span class="pill">mem0</span>
<span class="pill">Milvus</span>
<span class="pill-outline">장기 메모리 + 벡터 DB</span>

<div class="two-col">
<div>
<h3>9.1 mem0는 뭘 하고 Milvus는 어디 쓰나</h3>
<p>
<strong>mem0</strong>는 LLM용 <strong>장기 메모리 레이어</strong>로 보면 된다.
</p>
<ul>
<li>대화 내용, 사용자 정보, 과거 요청·응답 등을 <strong>"기억"</strong>으로 관리한다.</li>
<li>이 기억을 텍스트로만 두지 않고 <strong>임베딩 벡터</strong>로도 만들어 둔다.</li>
<li>"예전에 한 말"과 <strong>비슷한 상황이 오면</strong> 그 기억을 다시 찾아 LLM에 넣어준다.</li>
</ul>
<p>
이때 <strong>"기억 벡터를 저장하고 빨리 찾는 역할"</strong>을 Milvus가 맡을 수 있다.
</p>
<div class="note">
<strong>mem0</strong>는 무엇을 기억할지, 어떻게 요약·병합할지 결정하고, <strong>Milvus</strong>는 그 기억을 벡터 공간에서 빠르게 검색한다.
</div>
</div>
<div>
<h3>9.2 구성 예시 (개념용)</h3>
<p>mem0 설정에서 Milvus를 벡터 스토어로 지정하는 예시다.</p>

```
from mem0 import Memory

config = {
    "vector_store": {
        "provider": "milvus",
        "config": {
            "collection_name": "mem0_memory",
            "embedding_model_dims": 1536,
            "url": "http://localhost:19530",   # Milvus 서버 주소(기본 포트 19530)
            "db_name": "mem0_db",
        }
    }
}

memory = Memory.from_config(config)
```

<ul>
<li>`provider: "milvus"` → 벡터 검색을 Milvus에 맡긴다는 의미</li>
<li>`collection_name` → "기억"을 저장할 Milvus 컬렉션 이름</li>
<li>`embedding_model_dims` → 사용하는 임베딩 모델의 차원 수</li>
</ul>
</div>
</div>
